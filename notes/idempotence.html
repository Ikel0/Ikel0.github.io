Comment Routier traite la relecture d’un même événement Kafka

Le worker Kafka de Routier ne commite l’offset qu’après une réponse de l’API ou une écriture confirmée dans le topic de rejet. S’il s’arrête entre l’écriture en base et le commit, Kafka lui redonne le même message au redémarrage. Voici ce que devient ce message au deuxième passage.

ProjetRoutier, ingestion de télémétrie synthétique : worker Kafka, API Python, SQLite

Pourquoi le worker relit des messages

Le consumer du groupe routier-control tourne avec enable_auto_commit=False. Pour chaque message, il vérifie le contrat vehicle.telemetry en version 1.0, puis il poste l’événement sur POST /api/events, ou il publie le message invalide dans vehicle.telemetry.invalid.v1 et attend l’accusé du broker. consumer.commit() ne vient qu’après. Si l’appel à l’API échoue, la boucle s’arrête sans commit ; le worker patiente quatre secondes, se reconnecte et relit depuis le dernier offset commité.

Il n’y a pas de transaction commune entre Kafka et SQLite dans ce projet, donc annoncer du exactly once aurait été faux. J’ai choisi une livraison at least once et je l’affiche : GET /api/metrics renvoie "delivery_semantics": "at_least_once_with_idempotent_sink".

Ce que l’API répond au deuxième passage

Dans SQLite, event_id est la clé primaire de la table events et l’écriture passe par INSERT OR IGNORE. Au premier passage, une ligne est insérée et l’API répond 201 avec "status": "accepted". Au second, rien n’est inséré et la réponse devient 200 avec "status": "duplicate". Le worker traite les deux comme des succès, commite et passe au message suivant.

Chaque passage ajoute une ligne dans ingestion_audit, avec l’outcome (accepted, duplicate ou rejected), l’origine, le motif d’un éventuel rejet et un trace_id. Ce trace_id est formé de evt- et des 20 premiers caractères d’un SHA-256 de l’event_id. Une relecture porte donc la même trace que le passage initial, et les deux lignes se retrouvent côte à côte dans GET /api/audit. La table events n’ayant pas bougé, la file d’alertes de l’opérateur reste la même.

Même event_id, contenu différent

Routier ne compare pas les contenus. Si un producteur renvoie un event_id déjà vu avec un retard modifié, l’API répond duplicate et la première version reste en base. La fiche de contrat pose la règle en amont : le payload est immuable une fois publié et l’event_id doit rester stable d’une relecture à l’autre. Un producteur qui l’enfreint ne sera pas repéré par Routier.

Dans Courier API, qui reçoit des requêtes HTTP et non un flux, j’ai fait l’autre choix. L’en-tête Idempotency-Key est enregistré par clé API et par route, avec l’empreinte SHA-256 du corps sérialisé en JSON canonique. Même clé et même corps : la réponse stockée est renvoyée avec Idempotency-Replayed: true. Même clé, corps différent : 409.

Les tests et la vérification à la main

Le test test_idempotency_audit_and_acknowledgement_are_visible écrit deux fois le même événement critique dans une base temporaire. Le premier save_event renvoie inserted: True, le second False, et les métriques comptent un accepted et un duplicate. Il fait partie des 11 tests lancés par PYTHONPATH=src python3 -m unittest discover -s tests.

Sur l’interface, un second clic sur « Charger le scénario » renvoie 0 insertion et 4 doublons. Le chemin Kafka lui-même, commit et reconnexion compris, n’a pas de test automatisé : il se vérifie avec docker compose up --build puis scripts/publish_demo.py.
