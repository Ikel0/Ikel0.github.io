Brancher un modèle sur un entrepôt via MCP : les contrôles que j’exigerais

Le Model Context Protocol (MCP) permet à un assistant d’appeler des outils, dont des outils qui exécutent du SQL. Sa spécification laisse l’autorisation optionnelle, et le cas Supabase de juillet 2025 a montré ce qu’un agent trop privilégié peut faire sortir d’une base.

VeilleSpécification MCP, documentation OWASP, billet de Simon Willison et fil Hacker News sur le cas Supabase.

Ce que la spécification impose, et ce qu’elle laisse optionnel

Dans la version 2026-07-28, l’autorisation reste optionnelle. Quand elle est implémentée sur un transport HTTP, elle suit OAuth 2.1 ; un serveur lancé en local par stdio prend ses identifiants dans l’environnement. Les règles sur les jetons sont nettes : un serveur MCP doit vérifier que le jeton a été émis pour lui (l’audience, RFC 8707) et ne doit ni accepter ni transmettre d’autres jetons. Le guide de sécurité nomme ce dernier défaut « token passthrough » et note qu’il brouille la piste d’audit.

Le même guide recommande des portées minimales au départ, élargies opération par opération, Il range parmi les erreurs courantes les portées génériques (*, all, full-access), et son scénario d’attaque prend l’exemple d’une portée db:*.

L’injection arrive par les données que l’outil renvoie

Le cas Supabase a été publié par General Analysis et repris par Simon Willison le 6 juillet 2025. Un développeur utilise Cursor avec le serveur MCP de Supabase, connecté avec le rôle service_role, qui contourne la sécurité au niveau des lignes. Un attaquant dépose un ticket de support contenant des instructions. Quand l’assistant lit les tickets, il lit aussi la table integration_tokens et recopie son contenu dans le ticket, visible par l’attaquant.

Willison appelle cette combinaison la « lethal trifecta » : accès à des données privées, exposition à du contenu non fiable, moyen de faire sortir l’information. Ici, la table de tickets cumulait les deux derniers rôles.

La réponse de Supabase sur Hacker News

Dans le fil Hacker News sur le billet de General Analysis (470 commentaires), un ingénieur de Supabase décrit les mesures prises : lecture seule encouragée dans la documentation, résultats SQL encadrés par un texte qui dissuade le modèle de suivre des instructions, tests de bout en bout. Il les présente comme des atténuations, l’injection de prompt restant un problème non résolu. Plusieurs commentaires ajoutent que la lecture seule n’empêche pas la fuite si l’agent dispose d’un autre canal de sortie.

Les listes d’OWASP

OWASP tient un MCP Top 10, encore en phase de test pilote. On y retrouve l’élargissement progressif des droits (MCP02), l’injection par le contenu renvoyé (MCP06), l’absence d’audit (MCP08) et les serveurs MCP installés hors de tout inventaire (MCP09). Le Top 10 LLM 2025 donne, pour l’agentivité excessive (LLM06), un exemple directement transposable : un agent qui recommande des produits n’a besoin que de lire la table products, sans accès aux autres tables ni droit d’écriture. Il demande aussi que l’autorisation soit appliquée par le système en aval, dans le contexte de l’utilisateur.

Ma liste avant de brancher un entrepôt

Je n’ai pas encore déployé ce montage ; c’est la liste que je tire de ces lectures.

  • Un rôle dédié, en lecture seule, limité à des vues préparées pour l’usage. Jamais un compte de service administrateur.
  • Les droits appliqués par l’entrepôt (filtrage de lignes, masquage de colonnes) avec l’identité de l’utilisateur, jamais par une consigne dans le prompt.
  • Un jeton émis pour le serveur MCP, sans passthrough vers l’entrepôt.
  • Si l’agent lit du texte écrit par des tiers (tickets, avis clients, commentaires), aucun outil qui puisse faire sortir de la donnée : ni requête HTTP, ni écriture dans une table lue de l’extérieur.
  • Chaque requête SQL émise par l’agent journalisée avec l’utilisateur qui l’a déclenchée.
  • Les serveurs MCP autorisés inventoriés, comme n’importe quelle dépendance.

Aucune de ces mesures ne rend l’injection impossible. Elles réduisent ce qu’une injection réussie peut lire et l’endroit où elle peut l’envoyer.
