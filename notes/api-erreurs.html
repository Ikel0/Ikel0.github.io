Une API fiable doit expliquer pourquoi elle refuse.

Un statut HTTP donne une catégorie d’erreur. Il aide rarement, à lui seul, la personne ou le service qui doit corriger la requête. Une erreur utile garde une structure et un contexte.

Question de départUne personne peut-elle corriger sa requête sans ouvrir les logs du serveur ?

Le refus fait partie du contrat.

Une API n’est pas fiable parce qu’elle répond toujours avec succès. Elle est fiable parce que ses comportements prévus, y compris les refus, restent cohérents. Une donnée manquante, un droit insuffisant ou une clé déjà utilisée sont des situations attendues ; elles méritent une réponse exploitable.

Une erreur doit aider à agir.

  • Un statut qui donne la catégorie générale du problème.
  • Un type stable que le client peut reconnaître.
  • Un titre court, un détail concret et un identifiant pour retrouver l’occurrence.

Je distingue ce qui peut être montré au client de ce qui reste dans les journaux internes. Expliquer n’implique pas d’exposer une information sensible. L’objectif est de donner la prochaine action possible, pas de raconter l’implémentation.

La cohérence vaut plus que la quantité.

Une réponse d’erreur très bavarde peut devenir aussi difficile à consommer qu’un message vague. Un format stable est plus utile : il simplifie l’intégration, les tests et le support. Le client sait où chercher la raison du refus ; l’équipe sait où raccrocher l’observation technique.

Mise en pratique

Courier API expose un contrat OpenAPI et traite les erreurs, les clés d’idempotence et les webhooks comme des comportements du produit à rendre lisibles.
