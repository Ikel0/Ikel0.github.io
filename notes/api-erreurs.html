Courier API, refus par refus : ordre des contrôles et écart avec la RFC 9457

Un POST /v1/shipments sans en-tête Idempotency-Key reçoit un 400 et le corps {"detail": "Idempotency-Key header is required."}. Les refus de Courier API suivent tous ce format, celui de FastAPI par défaut : un objet JSON avec un champ detail. Voici les refus possibles, l’ordre dans lequel ils tombent et ce qui manque pour suivre la RFC 9457.

L’ordre des contrôles

FastAPI exécute la dépendance d’authentification avant de valider le corps, et mes contrôles d’idempotence et de métier tournent ensuite dans la fonction de route. Sans clé API, un corps invalide reçoit donc un 401 et non un 422. Avec une clé valide mais sans Idempotency-Key, le même corps donne 422 : la validation Pydantic passe avant mon contrôle d’en-tête.

Les refus, code par code

  • 401 : Missing X-API-Key header. ou Invalid API key., avec WWW-Authenticate: ApiKey.
  • 403 : une clé de démo, limitée à deliveries:read et deliveries:write, appelle /v1/shipments.
  • 429 : plus de 120 requêtes par minute pour une même clé (valeur par défaut, fenêtre glissante en mémoire), avec Retry-After en secondes.
  • 422 : corps refusé par Pydantic, ou URL de webhook refusée (HTTP simple, localhost, adresse IP privée).
  • 400 : Idempotency-Key absent ou hors de 8 à 255 caractères, curseur de pagination illisible.
  • 409 : même clé d’idempotence avec un autre corps, requête encore en cours sous cette clé, ou transition de statut interdite comme Cannot transition from created to delivered.
  • 404 : ressource absente, par exemple Shipment was not found.

Pour un 422 de validation, detail liste chaque champ fautif avec type, loc, msg et input : une ville oubliée apparaît sous ["body", "recipient", "city"].

Un refus survenu après la réservation de la clé d’idempotence (transition interdite, URL rejetée, colis introuvable) supprime l’enregistrement resté en état processing. La clé n’est pas consommée : renvoyée ensuite avec une transition autorisée, elle aboutit à un 200.

Retrouver un appel avec X-Request-ID

Chaque réponse porte un en-tête X-Request-ID : celui du client s’il en a envoyé un, sinon req_ suivi d’un UUID. Le middleware écrit au même moment une ligne d’audit (request_id, acteur, méthode, chemin, status_code, duration_ms) que l’on lit avec GET /v1/audit-events. Un client qui envoie X-Request-ID: client-abc-42 retrouve son 404 sous cet identifiant. L’identifiant est dans l’en-tête, pas dans le corps de l’erreur.

L’écart avec la RFC 9457

Les erreurs partent en application/json avec un seul champ detail, sans type, title ni instance. Cela se voit à deux endroits. Les trois cas de 409 ont le même statut et la même forme, si bien qu’un client ne distingue un conflit d’idempotence d’une transition interdite qu’en lisant la phrase anglaise. Et detail change de type selon l’origine du 422 : une liste d’objets quand Pydantic refuse le corps, une chaîne quand la garde SSRF refuse l’URL.

Passer à application/problem+json demanderait un gestionnaire d’exceptions global et un type stable par cas ; instance pourrait reprendre le X-Request-ID.

Ce que vérifient les tests

Les tests de tests/test_api.py vérifient les statuts (401 sans clé, 403 pour la clé de démo, 409 sur le conflit d’idempotence et sur la transition created vers delivered), mais aucun n’inspecte le corps d’une erreur. Commande : PYTHONPATH=src python -m unittest discover -s tests -v.
