Airflow 3.3.2 : une 404 qui ne révèle pas les backfills

Un code HTTP ne signale pas seulement le résultat d’une action. Il peut aussi révéler qu’une ressource existe. Airflow 3.3.2 corrige ce cas précis sur quatre routes de backfill.

RepèreAirflow 3.3.2 est publié le 17 septembre 2026. La correction concerne quatre endpoints qui portent un backfill_id dans leur chemin.

Une autorisation ne doit pas changer l’objet demandé

Un backfill Airflow est rattaché à un DAG. Les routes GET /backfills/{backfill_id}, pause, unpause et cancel désignent toutes un backfill par son identifiant dans l’URL. C’est cet objet qui doit servir à déterminer le DAG auquel l’utilisateur a accès.

Avant la version 3.3.2, lorsque l’identifiant du chemin ne correspondait à aucune ligne, ces routes pouvaient résoudre l’autorisation à partir du dag_id envoyé dans le corps ou la chaîne de requête. Deux cas devenaient alors distinguables : un identifiant inexistant renvoyait 404, un backfill existant mais rattaché à un DAG que l’appelant ne peut pas lire renvoyait 403. La différence de réponse permettait donc d’énumérer des identifiants de backfill à travers des DAGs inaccessibles.

La correction tient dans la source de vérité

La note de version est précise : les quatre routes autorisent désormais uniquement le backfill nommé dans le chemin. Un dag_id fourni à côté ne peut plus modifier la ressource contre laquelle le contrôle est effectué. Les routes qui ne nomment pas de backfill dans leur chemin — liste, création et dry_run — continuent à s’autoriser à partir de la requête. Les routes pause, unpause et cancel renvoient aussi un nouveau détail, Backfill not found ; un client qui filtrait sur l’ancien message doit être adapté.

Ce n’est pas une règle selon laquelle toute absence devient une 404. Airflow conserve une différence utile quand elle ne révèle pas une ressource cachée : une personne qui peut lire le DAG, mais n’a pas le droit de modifier son backfill, reçoit encore une 403 sur une opération d’écriture.

Cas sur une route nomméeRéponse après 3.3.2Ce que l’appelant apprend
Identifiant inconnu404Rien sur un éventuel DAG
Backfill existant, DAG non lisible404La même chose qu’avec un identifiant inconnu
DAG lisible, écriture non autorisée403La ressource est visible ; l’action est refusée

Cette matrice n’est pas une politique de sécurité universelle. Elle exprime le contrat de ces quatre routes. Le choix de masquer ou non l’existence d’une ressource dépend d’abord du modèle de permissions et du produit concerné.

Le test à conserver avec la route

Un correctif d’autorisation est facile à fragiliser lors d’une refonte d’API, surtout si le même identifiant apparaît dans le chemin, un payload et des paramètres. Je garderais trois tests de non-régression : une route avec un identifiant inexistant, la même route avec un backfill d’un DAG non lisible, puis une écriture sur un DAG lisible sans permission d’écriture. Les deux premiers doivent produire le même statut et le même détail de réponse ; le troisième doit rester un refus explicite.

Je testerais aussi qu’un dag_id contradictoire ne change rien à une route qui porte déjà un backfill_id. Ce n’est pas un test d’interface : il vérifie que l’objet autorisé est bien celui que la route a nommé.

Ce que cette note ne dit pas

La correction ne couvre que ces routes de backfill. Elle ne remplace ni une revue des permissions des autres endpoints, ni la configuration d’un gestionnaire d’authentification adapté à la production. La référence des permissions de l’API rappelle que chaque gestionnaire d’authentification traduit ces couples ressource/méthode dans son propre modèle de rôles ou de permissions.
