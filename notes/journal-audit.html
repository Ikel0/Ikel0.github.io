Le reçu d’audit de Pacte, champ par champ

Si je valide deux fois orders_clean.csv sous le même contrat, la table d’audit de Pacte garde une seule ligne. La seconde réponse porte replayed: true et la date du premier enregistrement. Ce comportement tient au calcul de l’identifiant de run, qui a aussi une limite.

ProjetPacte, qui écrit un reçu par couple fichier-contrat dans une table SQLite.

Le contenu d’un reçu

Chaque validation écrit une ligne dans la table validation_runs. On y trouve :

  • le nom du lot et l’empreinte SHA-256 de ses octets bruts ;
  • le nom, la version et l’empreinte du contrat, calculée sur son JSON canonique, clés triées ;
  • la décision et le score ;
  • le résultat complet en JSON (chaque anomalie avec le nombre de lignes touchées, le plan d’impact par consommateur) et un hash de ce JSON ;
  • la date d’enregistrement.

GET /api/runs/{run_id} renvoie ce résultat tel qu’il a été stocké. Un identifiant inconnu donne une 404 avec le message « Reçu introuvable ».

Le plan d’impact vient de la liste de consommateurs écrite dans le contrat. Pacte ne calcule aucun lineage à partir du code SQL, contrairement au lineage par colonne de dbt cité plus bas.

Le calcul de l’identifiant de run

L’identifiant vaut run_ suivi des 16 premiers caractères hexadécimaux du SHA-256 de la chaîne « empreinte du contrat:empreinte du lot ». Pour le lot propre et le contrat 1.2.0, cela donne run_f82057d352d726b7. Un index unique porte sur cette colonne.

Avant d’insérer, AuditLog.record cherche l’identifiant. S’il existe, la méthode renvoie la ligne existante avec replayed: true. Le test test_audit_receipt_is_idempotent_for_an_exact_input enregistre deux fois le même résultat et vérifie quatre choses : le premier reçu n’est pas un rejeu, le second l’est, les deux hash sont égaux, l’historique compte une ligne.

J’ai voulu cette règle pour ne pas confondre une nouvelle exécution avec une nouvelle donnée. Revalider un lot inchangé n’ajoute pas de décision à l’historique. L’interface affiche toujours « contrôlé le » suivi de la date du premier enregistrement, y compris après un rejeu.

Ce que l’identifiant ne capture pas

L’identifiant ne dépend que du contrat et du fichier. Si je modifie une règle dans validation.py sans toucher au contrat, revalider le même fichier renvoie l’ancien reçu avec l’ancienne décision. Pacte n’enregistre aucune version du code. Ajouter le hash du commit au calcul de l’identifiant corrigerait ce point ; je ne l’ai pas encore fait.

L’empreinte porte sur les octets, ce qui joue dans l’autre sens. Pacte lit les CSV en utf-8-sig : un fichier réenregistré avec un BOM donne les mêmes lignes, mais une autre empreinte, donc un nouveau run.
