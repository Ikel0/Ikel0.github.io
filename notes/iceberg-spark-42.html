Iceberg 1.12 et Spark 4.2 : le runtime qui manque est un signal

Spark 4.2 est sorti. Iceberg 1.12 publie des runtimes jusqu’à Spark 4.1. Le suivi du projet confirme que la 4.2 restait en validation mi-octobre : un artefact 4.1 ne devient pas, par proximité, une compatibilité déclarée.

RepèreIceberg 1.12.0 est sorti le 29 septembre 2026. Au 14 octobre, la prise en charge de Spark 4.2 était toujours suivie par la communauté.

Le support visible est dans les artefacts publiés

La page de téléchargement d’Iceberg 1.12.0 liste des runtimes pour Spark 3.5, 4.0 et 4.1. Pour Spark 4.1, la coordonnée publiée est iceberg-spark-runtime-4.1_2.13:1.12.0. Il n’y a pas d’artefact iceberg-spark-runtime-4.2_2.13 dans cette version.

Ce détail est plus utile qu’une lecture rapide de la numérotation. Un runtime Iceberg se branche sur les API de l’exécuteur Spark, ses extensions SQL et son catalogue. Le nom du JAR est donc une partie du contrat d’intégration, pas seulement une convention de packaging.

Le tableau décrit Iceberg 1.12, pas l’ensemble de l’écosystème. Il ne dit pas que Spark 4.2 est inutilisable avec Iceberg pour toujours ; il dit que la paire n’est pas livrée comme supportée dans cette version.

Le raccourci vers le JAR 4.1 a déjà une limite observée

Dans le ticket Apache qui suit Spark 4.2, une personne a demandé si le runtime 4.1 pouvait être employé en attendant. Elle rapporte ensuite une IncompatibleClassChangeError autour de SparkView. Ce retour ne vaut pas une matrice de tests complète, mais il montre pourquoi une résolution Maven réussie ne suffit pas à conclure à la compatibilité.

La réponse d’un collaborateur Iceberg est plus importante que cette erreur isolée : des éléments de support 4.2 existent, mais les binaires n’ont pas été inclus dans la 1.12 car ils demandaient encore des validations. C’est une frontière claire entre du travail en cours et une dépendance que l’on peut standardiser dans une plateforme.

Transformer la matrice en contrôle de déploiement

Pour une migration, je traiterais le couple Spark / Iceberg comme une dépendance unique dans le manifeste de l’environnement. Le contrôle de départ est simple : la version de Spark, la version Scala et le nom du runtime Iceberg doivent correspondre à un artefact officiellement publié pour la version choisie.

Avant un passage de version, je garderais ensuite un petit jeu de tests sur le catalogue réellement utilisé : lecture d’une table existante, écriture d’un lot, puis l’opération de maintenance qui compte pour l’exploitation. L’objectif n’est pas de prouver toutes les fonctionnalités de Spark ; il est de repérer tôt l’écart entre la dépendance résolue et les appels que le pipeline emploie réellement.

Une mise à niveau qui sépare deux décisions

Iceberg 1.12 apporte du support Spark 4.1 et retire celui de Spark 3.4. Spark 4.2, de son côté, ajoute entre autres des interfaces de CDC. Ces évolutions peuvent être intéressantes séparément, mais elles ne forment pas automatiquement un même palier de production. Tant qu’un runtime 4.2 n’est pas publié par Iceberg, la décision raisonnable est de conserver un couple supporté, ou d’assumer explicitement une validation locale hors support.
