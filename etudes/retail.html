Étude de cas

Retail Core Lakehouse, un pipeline qui refuse de publier quand un chiffre ne tombe pas juste

Retail Core Lakehouse est une plateforme data retail sur données synthétiques : huit sources, un DAG Airflow, un projet dbt sur DuckDB, une réconciliation ventes/paiements qui ferme la publication en cas d’écart, et un flash ventes statique sur GitHub Pages. Cette page explique pourquoi la publication est fermée tant que 24 contrôles, 78 tests dbt et deux rapprochements n’ont pas passé, et ce que ce choix a coûté.

ProjetRetail Core Lakehouse, démo publiée, code sur GitHub
StackAirflow 3.3.1, dbt-core 1.11.14 avec dbt-duckdb, DuckDB 1.5.3, Python 3.12, AWS émulé par LocalStack 4.14.0 (S3, Kinesis, CloudWatch), Terraform validé sans déploiement, Docker Compose, GitHub Actions et GitHub Pages

Le problème de départ

Je voulais la chaîne complète d’un retailer omnicanal, de la source brute au tableau que lit un responsable commerce le matin, avec une règle : rien n’est publié tant que ventes, paiements et événements ne racontent pas la même histoire. Et que chaque chiffre affiché vienne d’un rapport d’exécution, pas d’une constante dans le code.

Ce avec quoi il fallait faire

Aucune source réelle. Ventes, paiements, stocks, prix, clients et événements web sortent de src/generate_data.py avec la graine 42 : 12 produits, 160 clients, 640 identités sur quatre systèmes, 960 commandes, 960 paiements, 3 160 événements et 24 versions de prix, soit 5 928 lignes dans huit fichiers. Les volumes ne bougent pas d’un run à l’autre, les dates sont recalées sur l’heure de génération. Aucun compte AWS non plus : S3, Kinesis et CloudWatch sont émulés par LocalStack, et src/aws_local.py refuse tout endpoint qui n’est pas local.

Les décisions, et ce que j’ai écarté

Des données synthétiques à graine fixe plutôt qu’un jeu public. Un jeu réel aurait apporté ses propres écarts avant les miens, et avec la graine fixe une CI qui échoue signale un changement de code, pas de données. Le prix est connu : la réconciliation prouve que la chaîne n’abîme pas des montants produits cohérents, pas que des sources réelles se rapprocheraient.

Une réconciliation bloquante plutôt qu’un indicateur de qualité à côté du chiffre. Le DAG retail_core_daily compte six tâches, planifiées à 05 h 15, et publish_kpis ne s’exécute que si reconcile_platform a passé : 24 contrôles Python, les tests dbt, un écart d’unités nul entre commandes et événements d’achat (1 372 des deux côtés), et un écart ventes/paiements sous 0,005 € sur 73 328,13 €. Côté dbt, six tests singuliers dans dbt_tests/ font échouer le build au premier écart. Un modèle de contrôle en Python et SQLite recalcule par ailleurs ventes, stock et paiements à côté des 19 modèles, 78 tests (77 tests de données et 1 test unitaire) et 1 snapshot du projet dbt sur DuckDB : si le SQL et le script Python donnent le même total, l’erreur n’est pas dans une hypothèse partagée.

Le flash est statique. build_static_site.py précalcule les 12 combinaisons canal × période dans static-data.js, et dashboard/flash.js recalcule dans le navigateur le tableau par canal pour n’importe quel jour complet, à partir des séries quotidiennes publiées. Rien à héberger, et le calcul est testé par node --test dans la CI. Le bouton « Actualiser » relit l’instantané, il ne relance pas le pipeline, et le README le dit.

Ce que j’ai enlevé décrivait une cible que rien dans le dépôt n’exécutait. Deux commits, « Clarifier mon projet retail » puis « Simplifier mon tableau de bord », retirent le runbook et le document Word, puis le connecteur compatible Airbyte, le profil Snowflake d’exemple et le simulateur de Black Friday ; le second seul enlève 840 lignes. docs/IMPLEMENTATION_STATUS.md dit pour ce qui reste le mot exact : exécuté, émulé ou validé.

Ce qui a cassé ou surpris

Le tableau de bord affichait des chiffres d’un ancien run. Sans dbt_run_report.json, serve.py affichait 19 modèles et 78 tests repris d’un ancien run. Ces champs valent maintenant null et l’étape apparaît comme non exécutée. Même chose pour le KPI « Réconciliation » à « 0 écart » en dur et le bandeau « Plateforme vérifiée » en texte statique : les deux lisent désormais les rapports du run.

Le total du flash ne correspond pas à celui du run, et c’est voulu. Le générateur place les commandes entre « génération moins 29 jours » et l’heure de génération, le premier et le dernier jour sont donc partiels. Le flash les exclut et cumule 28 jours complets, d’où 71 160 € et 931 commandes sur la capture du 7 septembre, contre 73 328 € et 960 commandes pour le run complet. Le curseur ne propose que les jours qui ont 13 jours d’historique, parce que l’écart « 7 jours contre les 7 précédents » remonte jusque-là. Un commit dédié l’écrit dans la note « Méthode de calcul », qui dit désormais pourquoi 71 160 € est inférieur à 73 328 €.

Docker Compose exposait le cockpit, Airflow et LocalStack sur toutes les interfaces, ils n’écoutent plus que sur 127.0.0.1. La première peau du tableau de bord, sombre, avec cartes, icônes et faux profil connecté, ressemblait à un gabarit SaaS : refaite en clair, en polices système, une seule couleur réservée au négatif.

Ce que je referais autrement

LocalStack émule les API, il ne dit rien des quotas ni des coûts d’un vrai compte. Le code Terraform décrit un bucket S3, un flux Kinesis, une fonction Lambda, un rôle IAM et deux alarmes CloudWatch, il passe terraform validate et n’a jamais été appliqué. Et des données qui se réconcilient à 0,00 € par construction ne disent pas comment la barrière réagirait à un paiement en deux fois ou à un remboursement.

Si je recommençais, j’injecterais des écarts dans le générateur, un paiement manquant ou un doublon d’événement, pour montrer la barrière fermée et le chemin de correction. Je ferais déployer gh-pages par la CI, qui aujourd’hui vérifie le build sans publier. Et je commencerais par le flash ventes, arrivé en dernier, parce que c’est lui qui a fixé ce que le pipeline devait garantir.

Ce que je sais faire, et que cette étude montre

Cette étude montre un pipeline dont la publication dépend d’une barrière que j’ai écrite : six tâches Airflow, et publish_kpis qui n’écrit son manifeste que si les 24 contrôles, les 78 tests dbt et les deux rapprochements passent. Elle montre des tests dbt qui portent une règle métier, un seul prix courant par produit, un stock promettable jamais négatif, des prix recommandés bornés entre moins 5 % et plus 3 %, et un tableau de bord dont les champs dbt valent null tant que dbt_run_report.json manque. Tout se rejoue avec python3 run_demo.py, 12 tests Python et 7 tests Node, dans GitHub Actions aussi.
